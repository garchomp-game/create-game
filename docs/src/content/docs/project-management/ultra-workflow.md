最終更新日: 2026-07-31

このページは、Arena CoreでUltraを使って長時間の自律作業を進める際の正本です。
Ultraは調査、実装、局所検証を長く自律的に続けるために使います。
すべての検証を各変更で繰り返すための指定ではありません。

役割分担、単一writer、Goal Contract、独立監査、完了条件は
[Codex PM・サブエージェント運用](../codex-autonomous-operation/)を併用します。
メインエージェントはPM兼ゲームディレクターとして統合と採否を所有し、
読取調査は並行化してもworkspaceへ書くagentは一体にします。

## 基本原則

- 1ゴールで扱う主な採否判断は1件にする。
- 実装中は局所的な証拠を素早く取り、候補SHAを固定してから横断QAを行う。
- 同じSHA、設定、コマンドで得たgreen証拠を重複取得しない。
- 人間の操作感を自動probeで代替しない。
- 実測基準を満たしている処理を、予防だけを理由に最適化しない。
- 品質基準は維持し、検証の実行頻度とタイミングを最適化する。

## ゴール契約

Ultra開始時は、次の項目を短く固定します。

| 項目 | 内容 |
| --- | --- |
| 判断 | 何を採用、調整、棄却できる状態にするか |
| 対象 | 変更する機能、画面、モード、責務 |
| 対象外 | 今回変更しない隣接機能 |
| 完了条件 | 実装結果と必要な証拠 |
| QA段階 | 編集中、候補固定、採用前のどこまで進めるか |
| 停止条件 | 人間判断へ戻す条件 |
| 書込権限 | local-only、commit、push-main、GitHub Issue / Projectの許可範囲 |

「v0.8の残Issueをすべて完了する」のような複数の採否判断を含む目標は、
関心事ごとのチェックポイントへ分割します。複数Issueを連続して処理する場合も、
各Issueの候補SHAと検証結果を混ぜません。

## 自律反復の上限

- 1サイクルで扱うゲーム体験仮説は1件とする。
- 数値候補の自律反復は原則2回までとする。
- 3案目が必要な場合は、先行2案の棄却理由と不足情報を整理して人間判断へ戻す。
- UI、ゲーム数値、保存形式、計装、性能改善を同じ候補へ混ぜない。
- 共有責務の修正が必要になった場合は、元の仮説と分離できるかを先に判断する。

この上限は、明白な不具合修正や失敗テストの修復には適用しません。
設計判断のない細かな修正を止めるためではなく、根拠の薄い調整ループを防ぐために使います。

## QAの三段階

### 1. 編集中

目的は局所退行を早く見つけることです。

- `git diff --check`
- TypeScript型検査
- 変更対象のunit test
- 必要な場合だけ短い決定論fixtureまたは1～2 seed probe
- 触れた画面またはフローだけのE2E

候補固定前は、全E2E、全seed matrix、長時間probe、実GPU soak、公開smokeを実行しません。
5分以上かかる見込みのコマンドは、明確な障害調査を除いて次段階へ送ります。

### 2. 候補固定

目的はmainへ載せるcommit候補を確認することです。候補SHAごとに原則1回実行します。
編集中文脈のCheckpointがgreenになった後、PMが`main`へローカルcandidate commitを
作成し、独立監査と以下のQAをそのSHAへ結び付けます。修正した場合は新しいSHAとして
監査と必要なQAをやり直します。

- fast unit全件
- production build
- 変更領域のE2E
- 変更仮説に対応する短いprobe
- 関連するStarlight build

CIで同じ検証を実行する場合、ローカルとCIの両方を待つ必要はありません。
ローカルは変更箇所を確認し、共有CIはcommit SHAへ証拠を結び付けます。

### 3. 採用前

目的はリリース候補SHAを確定することです。最終候補へ1回だけ実行します。

- 全unit、全E2E、配布build
- 事前登録したrelease probe
- 保存migrationとruleset境界
- 必要な実URLsmoke
- 必要な人間プレイテスト

15分実GPU soakは、描画基盤、ゲームループ、同時オブジェクト上限を変更した場合、
性能基準へ違反した場合、または公開リリース前に限定します。
文言、限定UI、docsだけの変更では再実行しません。

## 変更別の最小ゲート

| 変更 | 編集中 | 候補固定 | 採用前の追加 |
| --- | --- | --- | --- |
| docs、文言 | 対象確認 | Starlight build | なし |
| CSS、限定UI | 型、対象unit | 対象E2E、画像 | 必要時だけ実URL |
| 純粋なゲームルール | 対象unit | 短い固定seed probe | release probe、手動所感 |
| 保存、履歴、ranking | 対象unit | migration、対象E2E | 旧形式とruleset境界 |
| 共通simulation、RNG | 対象unit | fast unit全件、関連probe | 全E2E、release probe |
| 描画、ゲームループ | 対象unit | build、対象E2E | 性能差がある場合だけsoak |

失敗、予想外の差分、共有契約の変更を検出した場合だけ、ゲートを一段広げます。

## 計装の採用ルール

計装は一律に削除せず、用途で分けます。

### Core

製品機能、保存契約、リリース判定に使う計装です。

- スコア、生存時間、死因、被ダメージ
- 武器成果、進行、ランキング適格性
- 決定論とruleset識別
- フレームp95、50ms超過、敵・弾・Pickup上限

### Analysis

候補比較や一時的な設計判断に使う計装です。

- AutoPilotの詳細判断
- ボスshadow
- 危険イベント後の緩和量
- 選択停止と再開挙動
- 候補固有のアブレーション指標

Analysis計装は観測build、debug hook、明示probeを基本とし、通常buildで常時計測しません。
新規追加時は次を明記します。

1. この値で何を判断するか。
2. どのIssueまたは採否が利用するか。
3. Coreへ昇格、Analysisで維持、削除を判断する時点。

利用中の計装を、参照確認なしに削除しません。性能問題が疑われる場合は、
計装ON / OFFの同一条件比較を行い、実測差がある処理から限定的に止めます。

## 文書とGitHubの更新

実装中は、作業メモまたはIssueコメントの1か所へ事実を集約します。
各小変更で`current-state`、実行計画、risk、decision、Issue、PRをすべて更新しません。

ソロ開発では`main`へ直接commitし、候補SHAをそのcommitで固定します。PR作成を完了条件にせず、
push後の`main` CIを共有証跡として使います。長時間作業のためにbranchやworktreeを増やさず、
feature flagと開発専用fixtureで候補を分離します。

commit、push、Issue / Project更新は別の許可範囲です。利用可能な資格情報だけを理由に
外部変更せず、現在の依頼が許可しない場合はローカルcandidateで停止します。

| 時点 | 更新先 |
| --- | --- |
| 作業開始 | Issueの対象範囲と開始状態 |
| 実装中 | 作業メモまたはIssueコメント |
| 候補固定 | candidate commit、必要な設計・プレイテスト資料 |
| 採否確定 | current-state、decision、未解決risk、Issue完了証拠 |

Decision logは選択肢の比較と判断が変わった場合、Risk logは未解決の危険が残る場合だけ更新します。
docs-only commit後に、変更していないruntimeのQAを繰り返しません。

## 停止して人間判断へ戻す条件

- 数値候補を2回試しても狙った方向へ改善しない。
- 自動probeと手動所感が逆の結論を示す。
- 複数モード、武器、rulesetへ影響が広がる。
- 既存の受け入れ条件を変更しないと採用できない。
- 新しいライブラリ、保存schema、公開APIが必要になる。
- 既知の基準を満たしているのに、追加最適化の目的を説明できない。
- 外部状態、資格情報、人間プレイがなければ採否できない。

停止時は、完了済み、未実施、判断が必要な点、再開コマンドを残します。
未完了を隠すためにテスト範囲を狭めません。

## 完了報告

Ultra終了時は次だけを簡潔に報告します。

- 変更したこと。
- 採用、棄却、保留の判断。
- 実行したQAと結果。
- 意図的に未実施とした採用前ゲート。
- 対象commit、PR、Preview。
- 次に必要な人間判断。

テスト件数やメトリクス全文は、必要なレポートまたはCIへ置き、会話へ重複転載しません。
